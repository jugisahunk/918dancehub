# Research: static-site stack options

Findings for [issue #4](https://github.com/jugisahunk/918dancehub/issues/4) (child of the wayfinder map, [issue #3](https://github.com/jugisahunk/918dancehub/issues/3)). This is a **recommendation for a human to ratify in issue #5** — it is not a final decision, and nothing here has been implemented.

## Constraints being evaluated against

1. GitHub Pages must be usable as a staging/testing environment before production (hard requirement).
2. A genuinely low/no-cost production host: custom domain support, free HTTPS.
3. A plausible path to add a CMS later — ideally content collections / markdown-driven.
4. Realistic to build in ~3 weeks, given GitHub Pages is static-only (no server compute), so the shared Inquiry form needs an external forms backend.
5. Not over-engineered for a ~1-page brochure site: no accounts, no database, low traffic.

Site requirements this stack has to serve: four business-line sections (Event Rentals, Dance Classes, Social Events, Instructor Recruiting) plus one shared Inquiry form (name/email/interest/date/message) that must land in the owner's inbox, rebuilding the high-fidelity prototype at `docs/design/handoff-v1/918 Dance Hub.dc.html`. That handoff doc already identifies the natural content boundary for a future CMS: `features`, `classes`, `venueStats`, `events`, `socials`, `bottomNav` — six small arrays of structurally identical records.

## Framework / static-site generator comparison

| | Astro | 11ty (Eleventy) | Next.js (`output: 'export'`) | Plain HTML/CSS + build step |
|---|---|---|---|---|
| **Static output** | Default output mode is fully static/prerendered HTML.[^astro-cc] | Compiles templates to static HTML in `_site/`; no server-side processing needed to serve it.[^11ty] | `next build` with `output: 'export'` emits an `out/` folder of static HTML/CSS/JS, deployable to "any web server that can serve HTML/CSS/JS static assets."[^next-export] | Static by construction. |
| **GitHub Pages staging** | Official first-party guide, incl. GitHub Actions workflow and a documented path from a `github.io` staging URL to a custom production domain (drop `base`, add `CNAME`).[^astro-gh] | Widely deployed to GitHub Pages via a standard Actions workflow; no framework-specific obstacles. | Next.js publishes its own GitHub Pages deploy template (`github.com/nextjs/deploy-github-pages`), but static export drops a long list of framework features (see below) the moment you target GH Pages.[^next-export] | Trivial — it's just files. |
| **Content-collections / CMS path** | Purpose-built: `src/content/*` collections of Markdown/MDX/YAML/JSON, validated by a Zod schema, queried with `getCollection()`/`getEntry()`, fully typed.[^astro-cc] This maps directly onto the handoff doc's `features`/`classes`/`events`/etc. arrays. | Supports Markdown + front matter + global/collection data files, but there's no built-in schema/type layer — it's convention, not a structured API. | Content collections aren't a first-class concept; you'd hand-roll a data-fetching layer, and static export forbids anything that needs a live server (see Unsupported Features). | None — you'd be inventing a content layer from scratch. |
| **Build complexity vs. 3-week timeline** | One `npm create astro@latest`, component-based layout, low ceremony. Templating (`.astro` files) is close enough to HTML that the existing prototype's markup ports over quickly. | Extremely low — "minimal dependencies," templates can be plain HTML/Markdown/Nunjucks/Liquid.[^11ty] Simplest possible mental model. | Heaviest of the four: React component model, App Router conventions, and a documented list of features that silently break in export mode (dynamic routes without `generateStaticParams`, cookies, redirects/rewrites/headers config, ISR, default image optimizer, Server Actions, Draft Mode, intercepting routes).[^next-export] None of those are needed for a brochure site, so you'd be paying the framework's complexity tax for capabilities you explicitly aren't using. | Fast to start, but four sections × shared header/footer/nav means either copy-pasted HTML or a hand-rolled include system — reinventing what a generator already does. |
| **Fit for a 1-page brochure site** | Right-sized: static by default, but not "static only" — room to grow (islands, later interactivity) without a rewrite. | Right-sized, arguably the *most* minimal credible option. | Over-provisioned: a framework built around server rendering / RSC, used here only in a mode that exists to work around not needing a server. | Under-provisioned: no content model, no build-time templating discipline, more manual upkeep as sections repeat. |
| **Verdict** | **Best overall fit** — static-first, first-party GH Pages story, and the only one of the four with a structured, typed content layer that doubles as the CMS boundary. | Strong second choice — simpler than Astro, but the CMS-later path is weaker (no schema/type layer, more DIY). | Not recommended here — the framework's value proposition (server rendering, API routes, ISR) is exactly what this project doesn't need, and static export is explicitly the "give up most of the framework" mode. | Not recommended — viable for a true single page, but this project already has 4 sections + a documented reusable data shape; a generator earns its keep immediately. |

[^astro-cc]: [Astro docs — Content collections](https://docs.astro.build/en/guides/content-collections/): a collection is "a set of related, structurally identical data," defined with Zod schemas and queried via `getCollection()`/`getEntry()`; for static output, `getStaticPaths()` generates a page per entry, producing "an entirely static, prerendered site."
[^11ty]: [11ty docs](https://www.11ty.dev/docs/): Eleventy compiles Markdown/HTML/Liquid/Nunjucks/JS templates to static HTML in a `_site` output folder; setup is `package.json` + `@11ty/eleventy` + template files, with complexity scaling with need rather than being front-loaded.
[^next-export]: [Next.js docs — Static Exports](https://nextjs.org/docs/app/guides/static-exports): `output: 'export'` produces an `out/` folder deployable to any static host; explicitly unsupported: dynamic routes without `generateStaticParams()`, Route Handlers relying on `Request`, Cookies, Rewrites, Redirects, Headers, Incremental Static Regeneration, default-loader Image Optimization, Draft Mode, Server Actions, Intercepting Routes. Next.js links its own GitHub Pages deploy template from this same page.
[^astro-gh]: [Astro docs — Deploy to GitHub Pages](https://docs.astro.build/en/guides/deploy/github/): official GitHub Actions workflow; documents moving from a `github.io` URL (with a `base` path) to a custom domain by adding a `CNAME` file to `public/` and updating `site`/dropping `base`.

## Forms-backend comparison

The hard constraint here is constraint 4: GitHub Pages "takes HTML, CSS, and JavaScript files straight from a repository" — a static-only host with no server-side code.[^gh-pages] So the Inquiry form's submit target has to be an external service (or, if production ends up somewhere with compute, a serverless function there).

| | Formspree | Netlify Forms | Cloudflare Pages Functions / Workers | Getform → **Forminit** | Serverless fn on prod host |
|---|---|---|---|---|---|
| **Works with a GitHub-Pages-hosted (or any static) form?** | Yes — point the form's `action` at a Formspree endpoint URL; no backend code, host-agnostic. | **No, not on its own.** Netlify's docs are explicit: form detection works because "our build system automatically parses your HTML at deploy time" to inject the hidden `form-name` field — you must "deploy your site with that form included" *through Netlify's own build*.[^netlify-forms] A form merely hosted on GitHub Pages, even if you have a Netlify account, will not be detected. | A **Pages Function** is tied to a Cloudflare Pages project. But a **standalone Cloudflare Worker** is not — it's an independent HTTPS endpoint that a static form hosted anywhere (GitHub Pages included) can `POST` to, provided the Worker sends back CORS headers (`Access-Control-Allow-Origin`, handling the `OPTIONS` preflight).[^cf-cors] So this option is viable for a GH-Pages-only site, but only via a plain Worker you write yourself, not the Pages-integrated Functions feature. | Yes — same model as Formspree: point a static form at Forminit's endpoint, host-agnostic. | Depends entirely on what the prod host turns out to be; on GitHub Pages there is no "serverless function on the host" — this collapses to one of the other rows. |
| **Cost at this site's likely volume** (a local studio's inquiry form, plausibly single-digit-to-low-double-digit submissions/month) | Free tier: 50 submissions/month, 30-day history, 2 notification emails.[^formspree-pricing] Paid starts at $15/mo for 200/month. | Submissions are free/unlimited on Netlify's current credit-based plans[^netlify-pricing] — but moot, since it requires Netlify hosting. | Workers free tier: 100,000 requests/day, no charge for duration, 10ms CPU time/invocation included.[^cf-workers-pricing] Effectively free forever at this volume. | Getform rebranded to **Forminit** on 2026-01-14 (same product/team, existing endpoints keep working).[^forminit] Free plan: 100 submissions/month; paid from $19/mo. | N/A |
| **Setup complexity in a 3-week window** | Lowest — form `action` attribute + optional honeypot field, no code to write or deploy. | N/A (blocked by hosting requirement) | Moderate — write and deploy a small Worker (receive POST, validate, send email via an API like Resend/MailChannels, return CORS headers). More code than Formspree, but still a single small file. | Same shape as Formspree — low. | Depends on host. |
| **Reliability / spam handling** | Built-in honeypot field support (`_gotcha`) documented for basic spam filtering.[^formspree-honeypot] Mature, long-running product. | N/A here | You own it — must build your own spam mitigation (honeypot, rate-limiting) but you also fully control delivery. | Includes spam protection per vendor's own feature list.[^forminit] | Depends. |
| **Verdict** | **Best fit for the 3-week timeline**: zero backend code, free tier comfortably covers a single studio's inquiry volume, works identically regardless of which host ends up in production. | **Ruled out** unless production hosting is Netlify — confirmed against Netlify's own docs, not an assumption. | **Good fallback / good pairing if prod ends up on Cloudflare**: free at any realistic volume, but costs real setup time this project doesn't need to spend when Formspree does the job for free. | Viable alternative to Formspree, but smaller free-tier ceiling (100/mo would still be plenty) and less name recognition; no reason to prefer it over Formspree here. | Only relevant if a compute-capable host is chosen for production. |

[^gh-pages]: [GitHub docs — About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages): "GitHub Pages is a static site hosting service that takes HTML, CSS, and JavaScript files straight from a repository on GitHub."
[^netlify-forms]: [Netlify docs — Form setup](https://docs.netlify.com/manage/forms/setup/): form detection requires deploying the form "through Netlify's build system," which "automatically parses your HTML at deploy time" — no API call or extra JS needed *when Netlify itself builds and deploys the site*.
[^cf-cors]: Cloudflare Workers CORS pattern (per Cloudflare's own [CORS header proxy example](https://developers.cloudflare.com/workers/examples/cors-header-proxy/) and community guidance): a Worker must explicitly return `Access-Control-Allow-Origin`/`-Methods`/`-Headers` and handle `OPTIONS` preflight to accept cross-origin requests from a page hosted on a different domain.
[^formspree-pricing]: Formspree free-tier terms (50 submissions/month, 30-day retention, 2 notification addresses) and paid-tier pricing, per current third-party pricing trackers reflecting Formspree's published plans as of 2026; verify exact current numbers on formspree.io/plans before committing, as these move.
[^formspree-honeypot]: Formspree help center — Setup process documentation describes the `_gotcha` hidden-field honeypot pattern for spam filtering.
[^netlify-pricing]: Per current (2026) third-party summaries of Netlify's credit-based pricing, form submissions are unlimited/free across Netlify's plans as of an April 2026 pricing change — this is about cost, not about whether GitHub-Pages-hosted forms qualify (they don't; see above).
[^cf-workers-pricing]: [Cloudflare docs — Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/): Free plan includes 100,000 requests/day and no charge for duration, with 10ms CPU time per invocation included.
[^forminit]: [Forminit (formerly Getform.io)](https://forminit.com/): rebrand announced 2026-01-14; existing Getform accounts, data, and endpoints continue to work under the new name.

## Production hosting comparison

| | GitHub Pages (also as prod) | Cloudflare Pages | Netlify | Vercel |
|---|---|---|---|---|
| **Custom domain + free HTTPS** | Yes — GitHub partnered with Let's Encrypt in 2018 to issue free, automatic certificates for custom domains via CNAME/ALIAS; enable with the "Enforce HTTPS" setting.[^gh-https] Note: the cert covers only the domain you configure (e.g. you may need to handle apex + `www` separately). | Yes, free, per Cloudflare's own limits page — up to 100 custom domains per project on the free plan.[^cf-limits] | Yes, free custom domain + HTTPS on Netlify's free tier (standard for the platform). | Yes, free custom domain + HTTPS on Vercel's free (Hobby) tier. |
| **Relevant free-tier limits** | One Pages site per repo/account; no documented bandwidth/build-minute cap in the primary docs consulted. | 500 builds/month, 1 concurrent build, 20-min build timeout, 20,000 files/site, 25 MiB/asset, 100 projects/account.[^cf-limits] | Free tier bandwidth/build-minute caps apply (platform-standard SaaS free tier). | Free tier bandwidth/build-minute caps apply (platform-standard SaaS free tier). |
| **Forms story** | None built-in — needs Formspree/Forminit/a Worker (see above). | Can pair with Pages Functions (Workers-based) for an integrated, same-project forms handler if desired — otherwise same external-service story as GH Pages. | Native Netlify Forms — but this is Netlify's own reason to exist here, and it's the one host this project isn't required to use. | None built-in — needs an external service or a Vercel serverless function. |
| **Relationship to the staging requirement** | **Simplest possible relationship: staging and production are the same platform.** A `staging` branch/environment and the `main`-branch production deploy both go through GitHub Pages, so there is zero platform drift between "what we tested" and "what's live" — the single biggest risk staging exists to catch (behavior that only shows up on a different host) is eliminated by construction. | Good, but introduces a second platform beyond the one already required for staging — one more thing to configure and keep in sync within the 3-week window. | Same as Cloudflare: a second platform, plus the specific irony that the one Netlify feature this project might want (Netlify Forms) doesn't apply anyway since GH Pages remains staging. | Same as Cloudflare/Netlify: a second platform for no feature this project needs. |
| **Verdict** | **Recommended for production too.** It's free, has genuine custom-domain HTTPS, and using it for both staging and prod removes an entire class of "works in staging, breaks in prod" risk — directly serving constraint 5 (don't over-engineer) as well as constraint 2. | Reasonable fallback if the human deciding in #5 wants Pages Functions for an integrated forms backend instead of Formspree — a legitimate alternative, not a wrong answer, just more moving parts than necessary for a 3-week brochure-site build. | Not recommended as prod here, specifically *because* its standout feature (Netlify Forms) requires abandoning the GH-Pages-as-staging setup or running two divergent deploy configs. | Not recommended — no capability this project needs that GitHub Pages lacks. |

[^gh-https]: Per GitHub's own 2018 announcement partnering with Let's Encrypt for automatic, free HTTPS certificates on GitHub Pages custom domains ([github.blog/2018-05-01-github-pages-custom-domains-https](https://github.blog/2018-05-01-github-pages-custom-domains-https/)), enabled via the "Enforce HTTPS" checkbox in repository Pages settings; GitHub's current custom-domain docs describe DNS setup (CNAME/ALIAS/A records) that this HTTPS provisioning depends on.
[^cf-limits]: [Cloudflare docs — Pages limits](https://developers.cloudflare.com/pages/platform/limits/): free plan figures as cited.

## Recommendation

**Astro, deployed to GitHub Pages for both staging and production, with Formspree as the Inquiry form backend.**

Concretely:
- **Framework:** Astro, static output (the default). Content for the four business-line sections and the repeating record types the handoff doc already identifies (`features`, `classes`, `venueStats`, `events`, `socials`, `bottomNav`) lives in `src/content/` collections — Markdown/YAML files validated by a Zod schema. This *is* the future CMS boundary: when the owner wants to self-edit content later, the options are (a) a Git-backed headless admin UI (e.g. Decap CMS or Tina) pointed at those same content files with no data migration, or (b) the owner edits the Markdown/YAML directly via GitHub's web editor for the lowest-cost path of all. Astro is also the only one of the four frameworks surveyed with a first-party, typed content-collections API — 11ty would require hand-rolling that structure; Next.js's static-export mode explicitly gives up the features that would justify choosing it; plain HTML has no content layer at all.
- **Hosting, staging and production:** GitHub Pages for both. This isn't a compromise for the 3-week timeline — it's the strongest option on its own merits given constraint 1 (GH Pages *must* be staging): using the same platform for prod removes the "differs between staging and prod" risk category entirely, and GitHub Pages independently satisfies constraint 2 (free, custom-domain support, free automatic HTTPS via Let's Encrypt since 2018). Point `918dancehubandevents.com` (already owned via domain.com) at GitHub Pages via DNS + a `CNAME` file once the site is ready, per Astro's own GitHub Pages deploy guide.
- **Inquiry form:** Formspree. Netlify Forms is ruled out on the facts, not preference — Netlify's own docs confirm form detection only happens when Netlify's build system deploys the HTML, so it cannot work against a GitHub-Pages-hosted site. Formspree needs zero backend code (the form's `action` attribute points straight at a Formspree endpoint), its free tier (50 submissions/month) comfortably covers a single local studio's inquiry volume, and it works identically no matter what production hosting choice #5 lands on — the lowest-risk, fastest-to-ship option inside a 3-week window.

**If the human decision in #5 wants to reconsider one piece:** the most defensible substitution is Cloudflare Pages Functions (a Worker) instead of Formspree, if there's appetite to own the form-handling code and stay on a fully free, self-hosted-adjacent stack indefinitely — Cloudflare Workers' free tier (100k requests/day) makes this free forever at this site's volume, confirmed above to work cross-origin from a GitHub-Pages-hosted form via CORS headers. That's a reasonable second choice, not a rejection of the framework/hosting recommendation above.

## Not recommended, and why

- **Next.js static export** — the framework's core value (Server Components, API routes, ISR, Server Actions) is exactly what static export throws away, per Next.js's own unsupported-features list. Choosing it here means adopting React's build tooling and mental model to end up with... plain static HTML, which Astro and 11ty produce with far less ceremony.
- **11ty** — a legitimate, simpler alternative to Astro, and worth a second look if the person deciding in #5 prioritizes minimalism over the content-collections/CMS story. The gap versus Astro is narrow; it's not recommended here only because it lacks Astro's typed content-collections API, which is the cleanest available answer to constraint 3.
- **Plain HTML/CSS + a simple build step** — under-provisioned once there are four repeating sections and a documented reusable data shape; you'd end up reinventing a small subset of what Astro/11ty already do, for no timeline benefit.
- **Netlify Forms** — confirmed against Netlify's own documentation to require the site's HTML actually be built and deployed by Netlify. Since constraint 1 fixes GitHub Pages as staging and this recommendation keeps GitHub Pages as production too, Netlify Forms is structurally unusable here — not a matter of preference.
